## Product slice

**User story:** As a visitor to the local demonstration app, I want to see the organization's reservable resources so I can tell what can eventually be booked.

This first slice is intentionally read-only and local. It establishes how a browser request travels through the frontend development server, HTTP, a Spring MVC controller, and an API response, then becomes rendered React UI.

### API contract

Implement these routes with in-memory data. The list and detail response use the same resource shape:

| Field | Type | Contract |
| --- | --- | --- |
| `id` | UUID string | Stable identifier for a resource. |
| `name` | String | Human-readable resource name. |
| `type` | String | One of `ROOM`, `DESK`, or `EQUIPMENT`. |
| `zoneId` | String | IANA time-zone identifier, such as `America/Los_Angeles`. |

- `GET /api/resources` returns HTTP 200 and a JSON array with at least three resources, including at least one of each type.
- `GET /api/resources/{id}` returns HTTP 200 and one matching resource, or HTTP 404 when the ID is unknown.
- Keep IDs and response contents stable between requests and application restarts. Do not generate random IDs during a request.
- Preserve a deterministic list order for repeated requests. Search, filtering, pagination, bookings, persistence, authentication, and a production deployment are out of scope.
- Do not use a client-supplied identity or claim that this local catalog is ready for public deployment.

### Frontend behavior

At the main page, load and display resource names and types from the API. The user can distinguish these four states:

1. Loading while the request is unresolved.
2. A successful response with resources.
3. A successful empty array, with a clear empty state.
4. A failed request, with a useful nontechnical message that does not expose a stack trace.

The page must render resource text as text, not interpret it as HTML. Include accessible page structure and meaningful names for interactive retry controls if you add one. Visual styling is not graded in this chapter.

## Session 2: Resource API and contract tests

**Prerequisite:** Session 1 is complete.
**Time:** 45-60 minutes.
**Deliverable:** In-memory list and detail endpoints meet the API contract, with focused Spring web-layer tests.

1. Before implementation, write test scenarios for the list response, every resource type, the detail response, and an unknown ID. Run them and confirm the failures are due to missing behavior, not a broken project setup.
2. Implement the smallest endpoint/controller path that meets those tests. Keep the data in memory and separate response DTOs from framework-specific details where useful; do not build a speculative repository or service framework.
3. Use deterministic UUIDs and data that remains identical across requests and restarts. Include representative room, desk, and equipment resources with valid IANA zone identifiers.
4. Test JSON field names, values, array shape, status codes, and stable ordering. Test the real HTTP JSON contract using Spring's web test support rather than only testing a Java method in isolation.
5. Start the server and inspect both routes through an HTTP client or browser. Confirm what happens for an unknown UUID.

**Tests you must write:**

- The list route returns HTTP 200, a JSON array, and all required fields for at least three resources.
- The list includes `ROOM`, `DESK`, and `EQUIPMENT` and has the same order and IDs across repeated requests.
- The detail route returns the matching resource by ID.
- An unknown valid UUID returns HTTP 404.
- If you choose to test malformed UUID paths, record Spring's observed response, but do not overconstrain a framework-default response that the course contract has not specified.

**Debugging observation:** Break at the request-mapping/controller boundary. Trace method, path, path variable, response object, serialized JSON, and status. Compare the observed JSON keys and value types with the contract; do not infer them from the Java class alone.

**Stopping point:** The focused backend test passes, both routes behave as specified when called directly, and no persistence layer has been introduced.

## Session 3: React catalog and component tests

**Prerequisite:** Session 2 is complete.
**Time:** 45-60 minutes.
**Deliverable:** React loads and displays API data with loading, empty, and failure states, covered by user-visible tests.

1. Write tests before the data-fetching UI. Mock the network boundary, not React component internals. Make the test able to hold a request unresolved so the loading state is observable.
2. Implement the resource list using the agreed response contract. Keep API base-address configuration out of component logic where practical. Do not hardcode a production URL.
3. Handle loading, empty success, non-empty success, and failed HTTP/network/response parsing states distinctly. Remember that `fetch` does not treat every non-2xx response as a rejected promise.
4. Add a Vite development proxy for `/api` to the backend. Use the same relative API path in development so the browser calls the frontend origin and Vite forwards the request.
5. Start both applications and verify the actual request and rendered response in browser DevTools. Check that React renders API strings as text.

**Tests you must write:**

- A pending request presents the loading state and then renders the resource names and types after a successful response.
- A successful empty array presents the empty state, not the loading or failure state.
- A failed HTTP status and a rejected network request present useful failure UI.
- Malformed JSON or an unexpected payload is not rendered as valid resource data.
- A resource name containing HTML-like text is displayed literally and does not create an element.
- Assertions use roles, labels, or visible text where appropriate; avoid snapshots as the only evidence.

**Debugging observation:** Use the browser Network panel to inspect request URL, initiator, status, response body, and timing. Then use a frontend breakpoint to inspect the parsed value and component state. Separate a transport error from a successful HTTP response with an invalid body and from a render error.

**Stopping point:** Frontend tests pass, Vite serves the page, Spring serves the API, and the page renders API-provided rather than locally duplicated resource data.

## Session 4: Trace and diagnose failures

**Prerequisite:** Sessions 1-3 are complete.
**Time:** 45-60 minutes.
**Deliverable:** One documented request trace and a debug log for three controlled local faults.

Do not change several things at once. For each fault: reproduce it, capture evidence, state a hypothesis, test that hypothesis, repair the cause, and add or retain a regression test. Make intentional faults only in the local development copy, then restore and verify the clean baseline.

1. **Wrong URL or proxy target:** Change one local route/base-address/proxy setting so the request misses the API. Identify the actual URL and status before fixing it.
2. **Unavailable backend:** Stop Spring while leaving Vite running. Inspect the browser error and distinguish this from a valid JSON error response.
3. **Unexpected response shape:** Locally change the response key or type in a controlled way. Trace where the contract stops matching, then ensure the UI presents failure rather than misleading empty or broken content.
4. **Origin/CORS investigation:** Temporarily make a browser request directly to the backend on a different origin, then observe the browser's Network and Console panels. Explain which origin differs and whether the browser's CORS policy or the server response is the blocker. Restore the Vite proxy afterward; do not fix the exercise by enabling permissive CORS for every origin.
5. Use VS Code Java breakpoints in the controller and browser JavaScript breakpoints in the request/render flow. If debugger setup consumes the session, complete one end-to-end breakpoint trace and carry remaining faults to the next session.

**Debugging notes template:**

```text
Fault and reproduction:
Expected behavior:
Observed URL / status / response or browser error:
Relevant backend and frontend breakpoint observations:
Hypothesis:
Evidence that supports or rejects it:
Root cause:
Repair:
Regression test that guards against recurrence:
```

**Stopping point:** The baseline is restored; all focused tests pass; the browser request trace and at least one fault investigation are recorded. Do not mark the other faults complete unless you actually investigated them.
